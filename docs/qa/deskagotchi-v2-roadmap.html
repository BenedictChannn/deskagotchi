Deskagotchi V2 Roadmap

A repo-grounded snapshot of what Deskagotchi is today, what V2 must feel like, and the concrete work needed to get from prototype to a usable long-term desktop companion.

Target V2 usable pet

Current State

Deskagotchi is already past a blank prototype. It has the native Electron shell, a transparent overlay pet, care interactions, a manifest-based pet package system, a local Hatch prototype, QA harnesses, and a cohesive monochrome LCD asset direction. It is not yet a fully satisfying Tamagotchi-like companion because the long-term care loop, evolution consequences, desktop feel, and some UX polish still need to mature. Custom pet generation is archived for V2 planning until the asset pipeline is designed properly.

What Works Now

Desktop shell

  • Electron, React, TypeScript, Vite runtime.
  • Transparent frameless pet overlay.
  • Always-on-top setting and tray controls.
  • Single-instance behavior and explicit quit path.
  • Crash-safe save file with backup recovery.

Pet overlay

  • Clickable pet surface with compact in-overlay care menu.
  • Sprite drag moves the native overlay window.
  • Health, feed, play, clean, medicine, and sleep flows stay in overlay.
  • Ball play expands to the current monitor work area.
  • Food cue renders during eating from package anchor metadata.

Simulation

  • Deterministic simulation with injected time.
  • Offline progression capped at 36 hours.
  • Tracks hunger, happiness, energy, cleanliness, health, affection, discipline, age, weight, mess, illness, and mood.
  • Current long-term thresholds: baby 1 day, child 3 days, teen 10 days, adult 21 days.

Pet packages

  • Built-in and custom pets use the same schema.
  • Packages include manifest, spritesheet, preview, icon, growth stages, animations, personality, care modifiers, and foods.
  • Import rejects unsafe paths, oversized entries, executable files, duplicate ids, invalid manifests, and missing assets.

Hatch prototype archived

  • Full panel accepts name, description, concept, personality, colors, accessory, and theme.
  • Local placeholder package creation is schema validated before install.
  • Import and export support `.deskagotchi-pet` packages.
  • User-facing custom pet generation is not part of the V2 critical path.

QA and validation

  • Lint, typecheck, Vitest, and package validation scripts exist.
  • Desktop QA covers launch, drag, overlay, play, lifecycle, renderer, pet assets, and item assets.
  • Contact sheets exist for pet and item asset review.
  • QA evidence is written under `.qa-runs/`.

Asset System State

LCD item atlas

Food, toy, medicine, clean, and sleep items are packed into a lightweight monochrome atlas. Pet packages reference item ids for favorite, liked, shared, and disliked foods. The current food icons are functional but not yet at the V2 recognizability bar.

Current visual direction

The approved V2 direction is monochrome LCD toy art: readable tiny silhouettes, limited palette, transparent sprites, compact icon-first care UI, and no large web-app panels in the normal pet overlay.

  • Runtime palette: LCD background, mid pixels, ink pixels, paper backing.
  • Pet frames stay pixelated and readable at small desktop sizes.
  • Generated source art belongs outside the packaged app unless needed for metadata.

Main Gaps Before V2

Care loop needs sharper consequences

The current simulation is deterministic and useful, but V2 needs clearer care deadlines, mistakes, illness duration, sleep/wake rhythm, and evolution branch consequences so the pet feels alive over weeks.

Custom pet generation is archived

Current Hatch proves package installation, but production custom generation is not simple enough to include casually. V2 should not promise user-facing Hatch until the generation, approval, packaging, QA, moderation, and failure-recovery flow is designed.

Assets need production discipline

Bao, Miso, Mochi, Peanut, and Puddles now look directionally good, but V2 should enforce consistent frame anchors, expressive eating and play frames, readable small-size silhouettes, recognizable food icons, and no row that looks static by accident.

Desktop behavior needs hardening

Dragging and multi-monitor support exist, but V2 needs more evidence across DPI scaling, negative-coordinate monitors, sleep/wake resume, startup restore, click-through state, and close-to-tray behavior. Frozen-window cleanup, tray recovery, and always-on-top correctness are release gates after the main companion features are improved.

Play is still MVP

Ball play is a good direction, but V2 needs a polished pet chase loop, no ugly boundary affordances, obvious exit, scoring or affection feedback, and good behavior on all monitor sizes.

Packaging readiness remains

Windows packaging exists, but V2 needs installer QA, update-safe save migrations, startup-on-boot validation, resource size checks, and a clear local data/export story.

End Goal For V2

V2 should feel like a small living creature on the laptop, not a normal web app in a window. The user can leave it running for weeks, drag it around, care for it without opening a full panel, feed it food that visually matches the pet, play with it, watch moods and growth change from care quality, and switch between original built-in pets while custom generation remains deferred R&D.

Product definition

  • Transparent always-on-top pet overlay is the primary app.
  • Full panel is only for management: settings, pet switch, import/export, and future archived Hatch experiments.
  • All normal care happens inside the compact overlay.
  • Built-in pets are original, cute, and cohesive.

Simulation definition

  • Real-time/offline progression feels fair but meaningful.
  • Care mistakes, discipline, sleep, illness, mess, play, and affection affect evolution.
  • Growth is measured in days, not hours.
  • The engine stays framework-agnostic and testable.
  • The care simulation spec is updated with every logic change.

Quality definition

  • Low idle CPU and memory overhead.
  • No stuck windows or unclosable panels.
  • No care button covers the pet in normal state.
  • Desktop hardening has evidence across launch, drag, lifecycle, play, monitor, always-on-top, and sleep/wake scenarios.
  • QA evidence exists before claiming desktop behavior is fixed.

V2 Success Criteria

Feature evidence

  • Overlay care works without opening management panels.
  • Five built-in pets pass package and visual QA.
  • Food icons are recognizable without labels.
  • Simulation rules are documented and tested.

Desktop evidence

  • Launch, drag, overlay, play, and lifecycle QA pass.
  • Frozen-window cleanup and tray recovery are tested.
  • Multi-monitor, DPI, always-on-top, and sleep/wake behavior have evidence.
  • Manual desktop acceptance is recorded.

Release evidence

  • `corepack pnpm run check` passes.
  • `corepack pnpm run qa` passes.
  • `corepack pnpm run build` passes.
  • `corepack pnpm run package:win` passes or has a documented release exception.

Roadmap To V2

Tranche 1

Stabilize the current companion surface

Remove remaining overlay friction: no accidental full panel opens from care actions, compact controls never cover the pet at rest, drag feels native, close/quit behavior is predictable, and play mode exits cleanly.

Ship blocker
Tranche 2

Upgrade the care simulation

Add explicit care deadlines, discipline calls, sleep/lights windows, illness duration, mess consequences, and stage-specific care scoring. Keep constants centralized, tests deterministic, and the living simulation spec updated with each rule change.

Core loop
Tranche 3

Finish the V2 pet asset bar

Re-QA Bao, Miso, Mochi, Peanut, and Puddles against the same checklist: stable size, readable silhouette, real animation motion, good eating cues, and consistent LCD style.

Visual quality
Tranche 4

Make food and play feel intentional

Use pet-specific food choices that animals actually like, keep shared foods simple, improve food icons until they are recognizable without labels, render the selected food while eating, and make Ball play feel like a pet chase interaction rather than a debug physics demo.

Interaction
Tranche 5

Archive Hatch and protect the package boundary

Keep the custom pet generation prototype out of the V2 promise. Preserve safe import/export and package validation, document the open design questions, and revisit Hatch after the core pet loop is good enough to justify generated assets.

Deferred R&D
Tranche 6

Harden desktop behavior and prove Windows readiness

After the main care, pet, food, and play features settle, verify frozen-window cleanup, tray recovery, always-on-top, startup-on-boot, sleep/wake recovery, high-DPI displays, multiple monitors, save migration, installer behavior, and resource size.

V2 Acceptance Checklist

  • Launching the app shows only the compact transparent pet overlay by default.
  • The pet can be dragged by the visible sprite without triggering a click.
  • Care controls do not cover the pet in the normal resting state.
  • Feed lets the user choose real food items with clear icons.
  • Food icons are roughly identifiable without reading labels.
  • Eating shows the selected food near the pet mouth or configured anchor.
  • Play mode uses the monitor as the play area and exits cleanly.
  • Clean, medicine, sleep/lights, and health stay inside the overlay.
  • All built-in pets have stable, expressive animation rows.
  • Offline simulation applies real elapsed time with fair caps.
  • Evolution depends on care quality, sleep, play, health, and missed care.
  • Care simulation docs match the implemented rules and constants.
  • Custom pet generation is explicitly deferred and not promised as a V2 feature.
  • Normal care gameplay works offline and does not require image generation or network access.
  • Frozen-window cleanup, tray recovery, explicit quit, and reset-position flows are tested.
  • Always-on-top, multi-monitor, DPI, sleep/wake, and startup restore behavior have QA evidence.
  • Windows installer works, tray quit works, and no window remains frozen after close.
  • QA artifacts exist for desktop behavior, renderer behavior, pet assets, and item assets.
